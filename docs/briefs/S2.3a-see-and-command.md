# Brief S2.3a — See and command

**Status:** agreed 7 Nov 2026.
**Read first:** `STATE.md`, `ARCHITECTURE.md`, `docs/DATA-MODEL.md`, D-003, D-007, D-009, D-013, D-019, D-020, D-021, D-022, D-025, D-027, D-029, D-030.
**Depends on:** S2.2c closed.
**Goal:** the squad can be seen and commanded in 3D in the browser, and the camera and controls feel the same as the approved squad test.

## Why now

After S2.2c the game runs, but nobody can play it. The squad test's controls were tuned by hand until they felt good, so this brief must carry that feel across rather than reinvent it. The interface, screens and sound follow in S2.3b, so the controls are checked before anything is built on them.

The design session set the direction for the world and data model (D-020 to D-030). Much of the core still reflects the squad test: one character per class, one island, and four gear slots. The core changes in S3. What this brief builds must not take on those assumptions, so that S3 changes the core without rewriting the screen.

The squad test is the reference for side-by-side comparison, and the maintainer supplies it.

## Decisions

1. **The core stays in charge.** Rendering reads state and events, and changes nothing. Input turns into commands.
2. **Smooth drawing.** The renderer interpolates, drawing the moments between 30-tick states, so movement stays smooth at any display rate. The core changes its state in place (S2.2a), so the renderer copies the positions it needs before each tick. It keys everything on entity IDs, and copes with any number of entities appearing or vanishing at once, because a gate will drop a zone's enemies together (D-021).
3. **Clicks answer at once.** Move markers and selection rings appear on the press, not on the next tick.
4. **The controls are D-003 and D-013, as ruled.** Any change needs a new register entry.
5. **Slow time lives in `packages/app`.** It runs ticks at 30% speed, with the squad test's limit of 6 seconds, recharging at 0.45 seconds a second.
6. **Feel values carry over unchanged,** and live together in one typed settings file, not scattered through input and camera code:

   | Value | Squad test |
   |---|---|
   | Camera distance | 34 to 150 |
   | Tilt | 0.82 to 1.2 radians, by zoom |
   | Tilt adjustment | -0.5 to +0.4, total held to 0.5 to 1.4 |
   | Starting zoom | 0.34 |
   | Zoom step | 0.08 a notch, easing at 9 a second |
   | Pan speed | 36 to 125 units a second, by zoom |
   | Rotation keys | 1.7 radians a second |
   | Middle drag | 0.006 radians a pixel for rotation, 0.004 for tilt |
   | Follow easing | 4 a second |
   | Camera margin | 20 units beyond the zone's size, which gives the squad test's 112 |
   | Drag threshold | 6 pixels |
   | `A` key delay | 150 milliseconds |
   | Click radius | 34 pixels for characters, 36 for enemies |
   | Box-select margin | 8 pixels |

7. **The camera limit is worked out, not stored.** It is the zone's size from the core, plus the camera margin. No camera value enters the core's data, because that would mix the look into the rules (D-022).
8. **The look stays at prototype level.** Low-poly placeholder art is correct here. The squad test used three.js r128, so light and colour are retuned here to match it under the current version. The work stops there, and art direction comes in S5 (D-030).
9. **The land comes from the zone** (D-021). `packages/app` gets the current zone's data from a named core read, and stops passing in `TEST_ISLAND`. The read gives zone data, not island data, because later zones will not all be islands. `createIslandView` becomes a zone view. This changes the core's and the renderer's public interfaces.
10. **A zone's scene can be dropped and rebuilt.** The renderer builds a scene from one zone, and can throw it away and build another, so that gates need no rework later (D-021). Colours are chosen by zone in one place in `render`, so each zone can have its own palette (D-022, D-030).
11. **Characters are handled by who they are, not by their class** (D-025). Drawing, selection and the keys `F1` to `F3` and `Z` `X` `C` work on each character and its place in the active three: first, second and third. Nothing in `render` or `app` assumes one character per class.
12. **Spell keys come from data** (D-027). Each character's keys `1` to `9` map to its spell list in order, read from data, not from a fixed map per class.
13. **What things look like comes from one lookup** (D-029). Class and monster names, and how each is drawn, come from one table in `render` keyed by type ID, with a plain default. A new class or monster type in the data never breaks the screen.
14. **Sniper replaces Shooter** (D-020). The code, tests, viewer and replays are renamed from `shooter`, and every label says Sniper. Replay hashes change once, on purpose.
15. **It runs in a browser on Windows, Mac and Linux.** The game is desktop-first (D-003) and expects a mouse.
16. **A test hook exists for browser tests:** a seed in the address and a way to speed up ticks.

## Scope

**In:**

- The zone's land, sea, sky, light, shadows and the props the core placed.
- Characters, monsters, the boss, projectiles, drops and effects.
- Telegraphs for every dangerous move.
- Health bars over characters and enemies.
- Selection, selection rings, the target ring, move markers and box selection.
- Camera: pan, grip, rotate, tilt, zoom, follow, snap and reset.
- Mouse and keyboard input from D-003 and D-013, including spell keys.
- Slow time and its limit.
- A clear message for browsers without WebGL.
- The rename from Shooter to Sniper.

**Out:**

- HUD, screens, the anvil, sound, floating damage text, hit-stop, fonts and the README link (S2.3b).
- Saves (S3, D-024).
- Placing characters in the triangle by their place in the three, and splitting `Unit` into the character and its live body (S3, D-025).
- More gear slots and item types (S3, D-028).
- Art, models and music (S5).
- Cities, NPCs, shops, inventory, quests and a second zone (S3).
- Touch controls and full trackpad support (no brief yet).
- Keyboard rebinding (no brief yet).
- A downloadable desktop app (no brief yet).
- Balance work (no brief yet).

## Done means

1. `pnpm check` passes.
2. `pnpm test:e2e` covers these flows in a real browser:
   - Move the squad with a right click.
   - Select one character with `F1`, and move only that character.
   - Box-select two characters.
   - Regroup.
   - Cast a spell with its key.
   - Grip, rotate and zoom the camera.
3. A smoke test starts the game in Chromium, Firefox and WebKit.
4. A right click moves the squad to the point under the cursor, measured at the squad's centre, with the camera at four different rotations.
5. A right drag never issues a move order.
6. The camera stays where the player left it after an order, unless follow is on.
7. A test proves the screen copes with a family of three Fighters: each is drawn, selected and given its own spell keys.
8. A test proves the renderer can drop a zone's scene and build it again without errors or leaks.
9. Replays are re-recorded for the rename only. Before re-recording, a run under the old and new names gives the same events on every tick, apart from the class name. The hashes change, and the new ones are recorded here.
10. A bot run from start to victory in the real page raises no console errors.
11. Frame rate is measured during the boss fight, in both the squad test and this build, and recorded here. There is no target for now.
12. `docs/DATA-MODEL.md` is updated for the rename.
13. A check on the tracked files and built site finds no secrets, local paths or unintended personal information.
14. The maintainer has approved the exact file list and diff before any commit.
15. CI is green on `master` after the maintainer's approved push.
16. **The maintainer has commanded the squad beside the squad test,** in a run up to and including the boss, and answered:
    - Did the camera do what your hands expected?
    - Did you feel like you were commanding a team, or babysitting one?
    - Could you follow all three during the boss?

## Stop and ask if

- Any control has to behave differently from D-003 or D-013.
- This build runs clearly slower than the squad test.
- The core needs a change beyond the zone read, the removal of `TEST_ISLAND` from the interface and the rename. Make such a change here only if its tests and replays still pass.
- Meeting decision 11 needs the core to stop assuming one character per class. That work belongs to S3, so record how far the screen gets without it.
- Any standing trigger in `CLAUDE.md` fires.

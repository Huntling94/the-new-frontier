# Brief S2.1 — Project scaffold

**Status:** draft.
**Read first:** `STATE.md`, `CLAUDE.md`, D-009, D-010, D-014, D-016.
**Depends on:** S1 closed, with the `v0-2019` tag on GitHub.
**Goal:** every change is checked automatically, and a working page shows an empty 3D island in the browser.

## Why now

The repository has documents and a preserved 2019 game, but no project for the new game to live in. Tooling comes before gameplay, so that every later line of code is checked from the moment it is written.

## Decisions

1. Use TypeScript, three.js, Vite, pnpm, Vitest, Playwright, ESLint and GitHub Actions on Node 24 (D-009).
2. Split the code into four packages (D-016):
   - `packages/core`: game rules, with no runtime dependencies, browser APIs, Node modules or three.js.
   - `packages/render`: everything drawn on screen.
   - `packages/app`: the page, input and interface.
   - `packages/tools`: command-line tools that run on Node through `tsx`, starting with the `legacy/` guard.
3. The island's shape is a pure function in `packages/core`, ported from the squad test. `packages/render` draws it, so the split between rules and drawing is proven from the first page (D-016).
4. Pin exact versions of Node, pnpm, TypeScript, three.js and `@types/three` (D-009). TypeScript stays at 6.0.3, because typescript-eslint does not yet support 7. Use a current three.js, with its types at the matching version, not the squad test's r128.
5. Keep the workspace private at package level. Nothing is published to npm (D-010).
6. Set Vite's `base` to `./`, so the build works at any address and does not depend on the repository's name (D-009).
7. **Nothing touches `legacy/`, and a guard proves it** (D-016). The guard reads git and changes nothing:
   - `git rev-parse HEAD:legacy` must equal `832123424d76aa3dbca94f8c0a8926219762f4f6`, the tree of `v0-2019`.
   - `git status --porcelain -- legacy` must be empty.
   - `git check-attr -a legacy/ge.c` must be empty.

   It runs in `pnpm check`, so a mistake is caught before a push, and again in CI.
8. **Line endings are set by named file type only:** `*.ts`, `*.json`, `*.yml` and similar. `.gitattributes` has no `*`, `*.txt` or `*.c` pattern. There is no `.editorconfig`, because a root rule could reformat legacy files on save (D-016).
9. CI does not compile `ge.c`. It needs Windows, and a failure could never be fixed because `legacy/` cannot change (D-016).
10. `pnpm check` means typecheck, lint, unit tests and the `legacy/` guard. CI runs that, then the build and browser tests, on every push (D-014).

## Scope

**In:**

- pnpm workspace with the four packages.
- Strict TypeScript settings shared across packages, with a `packages/core` config that has no DOM library and no ambient types.
- ESLint rules for `packages/core`: no three.js, DOM or Node imports, no dynamic imports, no `globalThis`, and no `Math.random`, `Date`, `performance`, `setTimeout` or `crypto`.
- Vitest with one real test in `core`, `render`, `app` and `tools`. The core's test covers the island's shape, and the tools test covers the `legacy/` guard.
- Playwright with one smoke test that the island renders, run on CI's software WebGL.
- An empty 3D island: terrain, sea, sky and light, with plain materials and no gameplay.
- GitHub Actions for install, `pnpm check`, build and browser tests.
- A Pages deploy that runs only after those checks pass, enabled according to the open question.
- `.gitignore` covering dependencies, build output, test results, `.claude/` and `.env` files.
- A Node version file, and `.gitattributes` as in decision 8.
- An inline favicon, so the browser test sees a clean console.
- `pnpm dev`, `pnpm build`, `pnpm check` and `pnpm test:e2e`.
- `ARCHITECTURE.md`, describing the packages and the rules between them.

**Out:**

- Matching the squad test's look (S2.3).
- Game rules (S2.2a).
- Monsters, the boss and the bot (S2.2b).
- Controls, characters and HUD (S2.3).
- The finished public page (S6).
- Any change to `legacy/` (never).

## Done means

1. On a clean clone, `pnpm install --frozen-lockfile` and `pnpm check` both pass.
2. `pnpm build` produces a static site with no errors.
3. `pnpm test:e2e` passes locally and on CI: the canvas shows several distinct colours, and the console has no errors. No screenshot baseline is committed.
4. Banned code fails lint. A test lints sample strings through ESLint's API, covering `three`, `document`, `Math.random`, `Date`, `performance`, a Node module and a dynamic import. No failing code is committed.
5. The `legacy/` guard passes, and a test shows it fails on a different tree hash.
6. Workflows use no secrets and pin actions to full commit hashes. Each job's write permissions are limited to `pages: write` and `id-token: write`, and only the deploy job has them.
7. Every new dependency has a licence compatible with MIT, and `NOTICE` lists those shipped to players.
8. Before each commit, a `git grep --cached` over the staged files finds no secrets, local paths or unintended personal information.
9. The maintainer has approved the exact file list and diff before any commit.
10. CI is green on `master` after the maintainer's approved push.
11. The maintainer has seen the island running: `pnpm dev`, then the address it prints.

## Stop and ask if

- Any workflow needs a secret, or a write permission beyond those in check 6.
- A required tool cannot run on both Windows and CI.
- Anything would alter a file under `legacy/`.
- Any standing trigger in `CLAUDE.md` fires.

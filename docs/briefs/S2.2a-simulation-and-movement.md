# Brief S2.2a — Simulation and movement

**Status:** agreed 7 Nov 2026.
**Read first:** `STATE.md`, `ARCHITECTURE.md`, D-001, D-003, D-009, D-015, D-016, D-018, D-019.
**Depends on:** S2.1 closed.
**Goal:** in a simple top-down viewer, the squad moves in formation around trees and rocks, and the same seed and commands replay exactly.

## Why now

The squad test proved the design, but its rules, drawing and input are tangled together in one page. Nothing can be tested without a browser.

This brief builds the foundation alone: time, randomness, state, commands, replays and movement. It proves D-015 and shows something on screen before nine spells are built on top. S2.2b adds combat and spells.

The squad test is the reference for behaviour and values. It stays outside this repository, and the maintainer supplies it to the builder.

## Decisions

1. **Fixed simulation:** the core advances 30 ticks a second, independent of frame rate (D-015). A tick is one small step of the game's rules. The rate is data.
2. **Seeded randomness:** all rule-affecting chance goes through one seeded generator, and its state is part of game state (D-015). Cosmetic randomness, such as grass tufts, sparks and camera shake, stays in `packages/render`.
3. **The core's public interface is named here** (D-019). `packages/core/src/index.ts` adds these exports:

   | Export | Does |
   |---|---|
   | `createGame(seed, scenario)` | Builds the starting `GameState`. A scenario is a named data record of what the game starts with |
   | `applyCommands(state, commands)` | Applies commands with no time passing, and returns events |
   | `advance(state)` | Runs one tick, and returns events |
   | `step(state, commands)` | `applyCommands`, then `advance`, and returns all their events |
   | `runReplay(replay)` | Plays a replay, and returns its final state and all its events |
   | `hashState(state)` | Returns the state hash |
   | `TICK_RATE`, `REPLAYS` | The tick rate, and the replays in `data` |
   | Types | `GameState`, `GameView`, `Command`, `GameEvent`, `Replay`, `Scenario` |

   `applyCommands` is separate because S2.3's anvil screen pauses ticks, and its commands must still land.
4. **The core changes its state in place,** because copying the whole game 30 times a second would not scale. Everything outside the core reads it as `GameView`, a read-only type. Anything that needs the previous tick, such as S2.3's smooth drawing, copies what it needs before stepping.
5. **Commands carry everything the rule needs** (D-015). The core has no cursor, camera or selection, and selection lives in `packages/app`. This brief's commands:

   | Command | Carries |
   |---|---|
   | `move` | Unit IDs, a world point, and whether it is an attack-move |
   | `regroup`, `scatter` | Nothing further |

6. **Events report what happened:** `order-accepted`, `order-refused` with a reason, `unit-arrived`, and `unit-gave-up` when a unit stops short of its destination. S2.2b and S2.2c add more. Events are plain data, and are not part of state or the hash.
7. **State is plain data** (D-015). Units refer to each other by ID, and IDs come from a counter in state. Nothing in `packages/core` keeps changing values outside `GameState`.
8. **Time:** data keeps the squad test's values in seconds. They convert to ticks once, rounded up, and state counts whole ticks. Per-second speeds divide by the tick rate.
9. **Order is fixed.** Commands apply at the start of a tick, in list order. Units update in ID order.
10. **A replay** is `{ seed, scenario, ticks, entries: [{ tick, commands }], expectedHash }`, and is typed data. `ticks` is how long it runs. `runReplay` rejects entries that are out of order or past the end, so none can be skipped silently. Replays are written by hand here, because no input exists until S2.3.
11. **The state hash** covers all of `GameState`, including the tick and the generator. It is a simple text hash of canonical JSON, meaning object keys are sorted. A number that is not finite is an error, so a broken value cannot hide.
12. **Changing rules or data changes hashes.** A failing replay test prints the new hash. Updating `expectedHash` is a deliberate edit, and the commit says why. CI's result is the reference.
13. **Replays must match in Node on CI.** Any difference on Windows is reported. Matching across browsers is not required.
14. **Movement follows the squad test:**
    - An order to all living units forms the triangle, facing the direction of travel.
    - An order to some of them puts those units in a line, and they hold that spot until regrouped.
    - Regroup orders all living units to the triangle at their centre.
    - Scatter dashes each unit away from the centre, then holds. It has a cooldown.
    - A point off the land is pulled in to 86% of the rim, along the line from the island's centre.
    - A unit with nothing to do and no hold returns to its triangle slot.
    - Units slide along obstacles, push apart from each other, and give up on a destination they cannot reach.
    - **The 30-tick result is the intended one for giving up.** The squad test's check depends on frame rate: at 60 frames a second, a unit walking freely gives up after about 8 units. At 30 ticks it arrives.
15. **Two values are stored now, and used later.** The attack-move flag has no effect until S2.2b. Scatter also sets the unit's invulnerability timer, which matters only once units can be hurt.
16. **Obstacles belong to the core.** Trees and rocks block movement, so their layout comes from the seed and lives in state. The beacon and waystone also block movement, at fixed places in the data. Each obstacle has a `kind`, and the renderer draws what the core placed.
17. **Zones are data** (D-015). The world is a list of one zone, built around `TEST_ISLAND`. This adds no new features.
18. **The viewer is dev-only.** It is `packages/app/viewer.html` with code in `packages/app/src/viewer/`, served by `pnpm dev` at `/viewer.html`. It is a plain 2D canvas, and it stays out of the build's input.
19. **Replays live in `packages/core/data/replays/`** and are exported from `index.ts`. The public page does not import them.
20. **Data stays separate** (D-018). Formation offsets, speeds, timings and ranges live in `packages/core/data`. So do the generator's and hash's constants.

## Scope

**In:**

- Tick loop, seeded generator, state, commands, events, replay and hash.
- Scenarios, with one empty scenario here.
- Zone data, walkable ground, and obstacles with no drawing.
- Three units with their squad-test positions and speeds, and no combat stats.
- Group and individual movement, triangle formation, hold position, regroup and scatter (D-001, D-003).
- One hand-written replay that shows all of the above.
- The dev-only viewer, which plays a replay and shows the tick and hash.

**Out:**

- Combat, the dummy, spells, XP, gear, upgrades and potions (S2.2b).
- The `target`, `cast`, `potion` and `upgrade` commands (S2.2b).
- Monsters, the boss, loot, wipes, auto-combat and bots (S2.2c).
- 3D drawing, audio, HUD and browser input (S2.3).
- Monster pools, the world graph and its validator (S3).

## Done means

1. `pnpm check` passes, with unit tests covering the generator, ticks and rounding, formation, line and hold, regroup, scatter, off-land points, obstacle sliding and units pushing apart.
2. Two runs with the same seed and commands end with an identical state hash, and a different seed gives a different hash.
3. The replay ends on its `expectedHash` on CI, and its events include no `order-refused`.
4. **Saving works mid-run.** A test turns state into JSON part-way through a replay, runs a different seed for some ticks, reloads the JSON, finishes the run and reaches the same hash. This proves nothing is hidden outside state.
5. A test shows `hashState` rejects a number that is not finite.
6. **The public build holds no dev code.** A check in `pnpm test:e2e` proves `viewer.html` is absent from `packages/app/dist`, and that no replay's `expectedHash` appears there.
7. The public page and its browser test still pass.
8. A check on the tracked files finds no secrets, local paths or unintended personal information.
9. The maintainer has approved the exact file list and diff before any commit.
10. CI is green on `master` after the maintainer's approved push.
11. The maintainer has watched the replay in the viewer: the squad moves in formation around obstacles, one character holds position, and the squad regroups and scatters.
